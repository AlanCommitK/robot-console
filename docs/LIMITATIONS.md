# 已知限制

本文列出 robot-console 当前的已知限制，以及在真实部署里需要补上的东西。每一项按"现状 / 影响 / 改进方向"记录，内容都对应当前代码和配置。设计取舍本身的理由见 [ARCHITECTURE.md](ARCHITECTURE.md) 第 6 节。

## 一、安全

### 1. 没有 TLS

- **现状**：Nginx 只监听明文 HTTP（容器内 80 端口，映射到宿主机 8080），浏览器和机器人都通过 `http://` / `ws://` 连接。前端会在页面是 https 时自动改用 `wss://`，但仓库里没有任何 TLS 配置。服务之间（API 到 PostgreSQL、Redis、RabbitMQ）也是明文。
- **影响**：JWT、登录口令、机器人 token 和命令内容在网络上可被窃听或篡改。在本机或可信内网使用时问题不大，跨网络部署时不可接受。
- **改进方向**：在 Nginx 或前置负载均衡上终止 TLS（443 端口、证书自动续期、HSTS）；机器人改用 `wss://`；视网络边界为数据库、Redis、RabbitMQ 开启 TLS。

### 2. 默认凭证和密钥放在环境变量里

- **现状**：所有凭证都是公开的开发默认值，并通过 `.env` / 环境变量传入：`JWT_SECRET`（API 启动时会对默认值打警告）、PostgreSQL 的 `robot` / `robot`、RabbitMQ 的 `guest` / `guest`、Grafana 的 `admin` / `admin`、种子账号 `admin` / `admin123` 与 `viewer` / `viewer123`，以及低熵的机器人 token `dev-token-robot-1` 到 `dev-token-robot-4`。为了降低风险，除 Nginx 外，发布到宿主机的端口都只绑定在 127.0.0.1。
- **影响**：任何知道默认 `JWT_SECRET` 的人都能签出 `role=admin` 的 token；默认口令一旦暴露在网络上就等于没有保护。环境变量还会出现在 `docker inspect` 的输出里。
- **改进方向**：用密钥管理服务（如 Vault、云厂商的 Secrets Manager、Kubernetes Secret）注入并定期轮换密钥；机器人 token 由机器生成（如 `secrets.token_urlsafe(32)`）并按台下发；去掉种子账号或强制首次登录改密；数据库按服务分配最小权限的账号。

### 3. 认证与用户模型做了简化

- **现状**：
  - 只有 `admin` 和 `viewer` 两种角色，没有按机器人或按组授权，任何管理员都能指挥任何机器人；
  - 用户只能由种子脚本创建，没有用户管理、改密、找回密码的接口；
  - JWT 在过期（默认 480 分钟）之前无法吊销，登出只是前端删除 token；没有刷新令牌；
  - 前端把 JWT 存在 localStorage，页面上的任何脚本都能读到；Nginx 没有设置 Content-Security-Policy 等安全响应头；
  - 机器人只凭一个静态 bearer token 认证，没有轮换机制，也没有设备证书。
- **影响**：权限粒度粗；凭证泄露后在有效期内无法止损；一旦出现 XSS，token 会被窃取。
- **改进方向**：接入 OIDC / SSO；短期访问令牌加刷新令牌，配合服务端吊销列表；把令牌放进 httpOnly Cookie 并做好 CSRF 防护，同时加上 CSP；按资源授权（机器人、站点、租户）；机器人改用 mTLS 证书或可轮换的凭证。

### 4. 没有限流

- **现状**：Nginx 没有配置 `limit_req` / `limit_conn`，后端也没有任何速率限制：登录、下发命令、换票、WebSocket 握手都不限次数。
- **影响**：登录接口可以被暴力尝试（bcrypt 让每次尝试变慢，但不能阻止）；失控的客户端可以刷爆命令队列或连接数。
- **改进方向**：Nginx 按 IP 限制请求速率和并发连接；登录失败退避或锁定；按用户、按机器人限制命令速率；限制每台机器人的未完成命令数。

## 二、可用性与数据

### 5. 依赖都是单实例，没有高可用和备份

- **现状**：PostgreSQL、Redis、RabbitMQ 各只有一个容器；RabbitMQ 队列是 classic 类型，没有副本；PostgreSQL 数据只在本地卷 `pgdata` 里，没有备份。API 有两个副本，但它们依赖的有状态服务都是单点。
- **影响**：任一依赖宕机时对应的功能不可用（具体行为见 [ARCHITECTURE.md 第 4 节](ARCHITECTURE.md#failure-handling)）；所在磁盘损坏时数据丢失。
- **改进方向**：PostgreSQL 流复制加自动故障切换（或托管数据库），配合定期备份和按时间点恢复；Redis Sentinel 或托管 Redis；RabbitMQ 集群加 quorum 队列（多副本、基于 Raft 的队列类型）。

### 6. 副本数量写死，WebSocket 连接不会重新均衡

- **现状**：两个 API 副本分别写在 `docker-compose.yml`、`frontend/nginx.conf` 的 upstream 和 `ops/prometheus/prometheus.yml` 的抓取目标里。Nginx 对 `/ws/` 也按轮询分配，但 WebSocket 是长连接：一个副本宕机后，机器人全部迁到另一个副本，原副本恢复后它们不会迁回（故障演练 1 中，`api-1` 恢复后 4 台机器人仍都连在 `api-2`）。
- **影响**：扩缩容需要同时改三处配置；故障恢复后负载长期不均衡，直到机器人因其他原因断线重连。
- **改进方向**：由编排平台做服务发现（如 Kubernetes Service 加 Prometheus 服务发现）；`/ws/` 改用 `least_conn`；副本恢复后由服务端有节制地关闭一部分连接，让机器人重连到负载较低的副本。

### 7. 历史数据无限增长

- **现状**：`telemetry` 和 `command_events` 表只写入、不清理，也没有分区；`commands` 表同样如此。
- **影响**：表和索引持续变大，遥测查询和清扫器的扫描都会逐渐变慢（清扫器查询条件只涉及非终态的行，代码注释建议的部分索引当前未创建）。
- **改进方向**：遥测按时间分区（或改用 TimescaleDB 之类的时序扩展）并设置保留期，旧数据降采样归档；为清扫器加部分索引；对命令和事件流水制定归档策略。

### 8. 健康检查不区分"存活"和"就绪"

- **现状**：`/api/health` 同时检查数据库、Redis 和 RabbitMQ，任一失败即返回 503，Docker 的 healthcheck 也用它。Docker 不会重启 unhealthy 的容器，`restart: unless-stopped` 只在进程退出时生效；开源版 Nginx 也只有被动的失败计数，没有主动健康检查。
- **影响**：在 Compose 下这没有坏处，但如果直接搬到 Kubernetes 用作存活探针，一个依赖故障会让所有副本被反复重启。
- **改进方向**：拆成存活探针（只看进程和事件循环是否正常）和就绪探针（检查依赖），由编排平台据此决定重启还是摘流量。

## 三、消息与一致性

### 9. 至少一次投递要求机器人侧去重

- **现状**：命令可能被重复投递（断线重连、副本宕机、broker 重启后的重投）。模拟器用一个容量 1000 的内存 LRU 集合按 `command_id` 去重，进程重启后就忘了。
- **影响**：真实机器人如果不去重，或去重窗口太短，同一条命令可能被执行两次。
- **改进方向**：机器人侧持久化已执行命令的 id，保留时间要覆盖可能的重投窗口（TTL 加最长离线时间）；对非幂等的动作（如"前进 1 米"）在协议里改成幂等的表达（如"移动到坐标"），本项目的 `move_to` 已经是这种形式。

### 10. 机器人上报的结果没有应用层确认

- **现状**：模拟器把 `ack` 和 `result` 写进 WebSocket 就算发出，服务端不回确认。服务端写库失败（例如 PostgreSQL 暂时不可用）或进程在处理前崩溃时，这条结果就丢了。断线期间产生的结果只排在模拟器内存里，进程重启也会丢。
- **影响**：命令最终由清扫器收尾：停在 `acked` 的在 `RESULT_TIMEOUT_S`（默认 300 s）后被标为 `failed`，停在 `dispatched` 的在 TTL + 60 s 后被标为 `expired`。机器人实际执行成功的命令可能被记为失败或过期，而且要等几分钟才有结论。
- **改进方向**：服务端在结果写库成功后回一条确认，机器人在收到确认前持久保存并重发结果（结果处理本身已经是幂等的）；为长时间执行的命令增加进度心跳，代替单一的结果超时。

### 11. Redis pub/sub 发后即忘：长连接的看板可能显示过期的命令状态

- **现状**：命令状态通知经 Redis pub/sub 推送，订阅断开期间的事件和发件箱里发布失败的事件都会丢失。已有的缓解措施：看板的 WebSocket 断线重连后会用 REST 重新拉取数据；界面上的命令状态按版本只进不退；状态本身始终以 PostgreSQL 为准。机器人的在线状态会自愈：实时连接正常时，前端只把最近 6 s 内收到过数据的机器人显示为在线。
- **影响**：Redis 短暂中断时，浏览器到 API 副本的 WebSocket 并没有断开，前端不知道自己错过了事件，也就不会重新拉取。期间发生状态变化的命令会一直显示旧状态，直到这条命令再有新事件、用户切换机器人、刷新页面或看板重连。
- **改进方向**：订阅任务重新订阅成功后，向本副本的看板推送一个"请重新同步"的事件（或主动关闭它们，让前端走重连校正）；或者给事件加序号，让前端发现缺口后自行拉取；需要可回放时改用 Redis Streams。

### 12. 幂等键永久保存，且不比对请求体

- **现状**：`(robot_id, idempotency_key)` 的唯一约束没有过期时间；同一个键配不同的请求体，返回的是第一次创建的命令，不报错；`publish_failed` 的命令也会被同一个键原样返回。
- **影响**：客户端误用同一个键发送不同的命令时得不到任何提示；键会一直占用唯一索引。
- **改进方向**：保存请求体摘要，键相同而请求体不同时返回 409 或 422；为幂等键设定保留期（例如 24 小时）后清理。

### 13. 停止命令和普通命令共用一条队列

- **现状**：`stop` 和其他命令一样进入这台机器人的队列。`prefetch_count=1` 意味着前一条命令被机器人 ack（或判定 ack 超时，最长 `ACK_TIMEOUT_S` = 10 s）之前，`stop` 不会被下发；机器人离线时 `stop` 会在队列里等待，最终过期。
- **影响**：模拟器收到命令立刻回 ack，所以实际延迟是毫秒级；但对一台回 ack 很慢或通信不稳定的真实机器人，停止指令可能被延迟最多 10 s。
- **改进方向**：真实系统的急停不能只依赖云端链路，必须由机器人本地的安全机制兜底；云端可以为停止类指令单独开一条高优先级的通道（独立队列或直接经 WebSocket 下发），并允许它越过排队中的普通命令。

### 14. 按机器人分队列的扩展上限

- **现状**：
  - 每个副本只有一条 AMQP 连接，每台在线机器人占用其中一个 channel；RabbitMQ 默认每条连接最多协商 2047 个 channel（本栈协商值即为 2047），所以一个副本同时服务的机器人数量上限约为 2000；
  - 每台机器人一个持久队列，队列一经创建就一直保留，下线的机器人不会被清理；
  - TTL 和死信交换机写在队列声明参数里，修改 `COMMAND_TTL_MS` 必须先删除已有队列，否则声明会因参数不一致失败。
- **影响**：机器人数量上千之后，channel 上限、broker 上的队列元数据和每队列的监控指标都会成为压力；调整 TTL 需要停机操作。
- **改进方向**：每个副本使用多条 AMQP 连接分摊 channel；用 RabbitMQ policy（而不是声明参数）设置 TTL、死信交换机和队列过期（`expires`），便于在线调整并自动清理闲置队列；机器人数量再大时，改为按机器人哈希分片的少量队列，或使用 RabbitMQ Streams / Kafka 一类面向海量分区的方案。

## 四、可观测性

### 15. 告警没有通知渠道，也没有日志聚合和链路追踪

- **现状**：告警规则只在 Prometheus 里计算，没有部署 Alertmanager，告警只能在 http://localhost:9090/alerts 查看；日志是每行一个 JSON 对象，但只留在 `docker compose logs` 里；request id 能在 Nginx 和 API 的日志之间对上，但没有分布式追踪。
- **影响**：告警触发时没有人会收到通知；排查跨组件的问题需要手动对照多个容器的日志。
- **改进方向**：部署 Alertmanager，按级别路由到邮件或即时通讯工具；把日志收集到 Loki 或 ELK 一类的系统；接入 OpenTelemetry，把 request id 扩展成跨 HTTP、RabbitMQ 消息和 WebSocket 的 trace。

## 五、范围

### 16. 只有模拟机器人

- **现状**：机器人由 `simulator/` 模拟：二维平面上的匀速运动、简化的电量模型、按固定概率"遇到障碍"失败。命令只有 `move_to`、`set_speed`、`stop` 三种，协议是项目自定义的 JSON over WebSocket。
- **影响**：没有覆盖真实机器人的问题：弱网和长时间离线、固件版本差异、本地安全约束、路径规划与多机避障。
- **改进方向**：为真实机器人实现适配层（例如对接 ROS 2 或 MQTT），给协议加版本号；按机器人型号声明支持的命令；在机器人侧实现持久去重、结果重发和本地急停（见第 9、10、13 项）。
